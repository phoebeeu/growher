# v1 → v2 产品迁移说明

日期：2026-08-15  
目的：把现有“多目标孕期任务助手”迁移为“单一项目陪伴推进器”。

## 1. 方向变化

| v1 | v2 |
|---|---|
| 工作、副业、运动体重、孕产准备四类目标 | 一次只选择一个有最终成果的个人项目 |
| 目标 → 周计划 → 今日任务 → 能量重排 → 总结 | 目标成型 → 契约计划 → 项目首页 → 陪伴执行 → 成果板 |
| 每日管理多个任务 | 每日只推进一个行动 |
| 独立总结页 | 成果摘要直接进入每日项目首页，成果板提供完整视图 |
| 两次能量评分和复杂重排 | 三种状态：正常推进、今天轻一点、今天休息 |
| AI 负责拆分大量任务 | AI 负责检查可行性、生成阶段和未来 7 天 |

## 2. 可以复用的基础

- Supabase 邮箱验证码登录、用户身份和 RLS 基础。
- Cloudflare Pages/Workers、GitHub 私有仓、`growher.site` 域名和自动部署链路。
- 现有 React/Vite 工程、响应式外壳和 DESIGN.md 的视觉令牌。
- 用户档案中的孕周字段；只保留为首页辅助信息，不扩张成医疗模块。

## 3. 需要替换或收缩的部分

- 四类目标表单改为目标成型器与单一项目契约。
- 周重点页改为阶段计划 + 未来 7 天；不生成完整周期的密集任务表。
- 今日状态页只保留三个状态，不再显示能量数值和多维问卷。
- 今日行动只显示一条，并支持标准/最低行动两档。
- 总结页的主要反馈并入首页；完整历史放入成果板。
- 原有 checkup、复杂 daily task 重排逻辑先保留兼容读取，再逐步退出主流程。

## 4. 建议的数据迁移顺序

1. 保留 auth/profile，新增单一项目及契约实体。
2. 新增阶段、未来 7 天计划、每日会面记录和成果格记录。
3. 建立“每个用户最多一个 active 项目”的数据库约束。
4. 新首页先使用新数据；旧数据不自动转换成新项目，避免把多个旧目标错误合并。
5. 新流程稳定后，再下线旧页面和旧写入路径。

## 5. 30 分钟内的最短开发路径

1. 先完成新项目契约、项目首页、陪伴执行、成果板的假数据纵向闭环。
2. 再接 Supabase 的项目、每日记录和成果格读写。
3. 本地完成一次完整流程测试后推送 feature branch。
4. Cloudflare 预览环境验收通过后再合并 main。
5. 视觉细节、导出图片和通知细节放在闭环之后。

## 6. 不变的上线纪律

- 不直接修改生产分支；先 feature branch、预览、验收、合并。
- 不在未确认的产品规则上继续扩展数据库和 API。
- 线上公开站点在新版规格获确认前保持现状。
